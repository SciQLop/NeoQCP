# Milestone 6 vocabulary

Every API name the target programs in `examples/user-code/` use that does not exist today, once, with the signature
the targets assume. Rows for existing names only where a target relies on behaviour that differs from today. A later
target reuses a row when the idea is the same; a new idea gets a new row.

Kind: **new** (not in `src/`), **reshaped** (exists under this or a close name, changes shape), **exists** (same
name and signature, different behaviour).

| Name | Signature | Kind (new / reshaped / exists) | Used by | Replaces (today's form) |
|---|---|---|---|---|
| `QCPItem` | `class QCPItem : public QCPLayerable, public QCPDrawable`; the base of every annotation, built-in ones included. Constructors take the item's own arguments only | reshaped (rename of `QCPAbstractItem`) | asteroids, brick-breaker, callout, peak-fit | `QCPAbstractItem(QCustomPlot*)`: the constructor took the plot, so every subclass forwarded it |
| `QCPPlottable`, `QCPPlottable1D<D>` | `class QCPPlottable : public QCPLayerable, public QCPDrawable`; `template <class D, class Base = QCPPlottable> class QCPPlottable1D`. Same short-names rule as `QCPItem`, `QCPArea`, `QCPAxisBase`: a 3.0 base drops `Abstract`, for both families | reshaped (rename) | lollipop | `QCPAbstractPlottable`, `QCPAbstractPlottable1D<D>` |
| `QCPAxisRect::add<T>(args...)` | `template <typename T, typename... Args> qcp::HandleFor<T> add(Args&&... args)`, for every family: builds `T(args...)`, binds it to the rect's `xAxis()` / `yAxis()` system, and for an item clips it to the rect and puts it on the `annotations` layer. The args are always constructor arguments. Built-in plot types gain data constructors (`QCPGraph(keys, values)`), so `add<QCPGraph>(x, y)` still reads the same | reshaped | lollipop, asteroids, brick-breaker, callout, peak-fit | two meanings today: a plottable's args go to the handle's `setData` (which a user type's handle lacks) after `new T(keyAxis, valueAxis)`; an item's go to `new T(&plot, args...)`, and only `QCustomPlot::add` takes items |
| `QCPPlottable1D<D>(keys, values)` | `template <QCPNumberRange K, QCPNumberRange V> QCPPlottable1D(const K& keys, const V& values)`: one `D(key, value)` per pair, sorted by key. A user type takes it with `using QCPPlottable1D::QCPPlottable1D;` | new | lollipop | only `(QCPAxis*, QCPAxis*, QCP::Capabilities)`, repeated by every subclass, and a `setData` each 1D type writes on `mDataContainer` |
| `QCPPlottable1D<D>::at` | `const D& at(int index) const` | new | lollipop | protected `dataAt(i)` (a pointer), or `dataMainKey(i)` / `dataMainValue(i)` |
| `QCPNumberRange` | `template <typename R> concept QCPNumberRange = std::ranges::input_range<R> && std::convertible_to<std::ranges::range_value_t<R>, double>;` ("any range of numbers goes in") | new | lollipop, callout, peak-fit | `QVector<double>` and `std::vector<double>` overloads |

| `QCPDrawContext::setDataIndex` | `void setDataIndex(int index)`: the commands recorded after it belong to data point `index` (-1: none). The default hit test, the rubber band and `stSingleData` selection then answer per data point. The selection decorator does not restyle a user type's commands: `draw()` reads `selection()` and records the selected look itself. Named after the library's "data index" (`dataCount()`, `QCPDataSelection`, `contains(int dataIndex)`) | new | lollipop | a hand-written `hitTest` override that recomputes the geometry the recording already has |
| `QCPDrawContext::setPart` | `void setPart(int part)`: the commands recorded after it belong to `part` of an item (0 before the first call). A hit answers the last recorded command under the cursor, the topmost one, and reports its part in `QCPMouseEvent::part()` | new | callout, peak-fit | an int `switch` in `anchorPixelPosition()` plus a pixel hit test written by hand |
| `QCPDrawContext::line` | `void line(QCP::Position a, QCP::Position b, const QPen& pen)` | new | lollipop, peak-fit | `polyline(std::span<const QCP::Position>, pen)` over a two-element array |
| `QCPDrawContext::circle`, data radius | `void circle(QCP::Position centre, double radius, const QPen& pen, const QBrush& brush = { })`: `radius` in data units on each axis, so the circle is an ellipse in pixels when the axes scale differently, and matches data-space geometry | new | brick-breaker | `ellipse(a, b, pen, brush)` from two corners |
| `QCPDrawContext::circle`, pixel radius | `void circle(QCP::Position centre, QCP::PixelLength radius, const QPen& pen, const QBrush& brush = { })`: a fixed-size disc on a position | new | lollipop | `markers()` with a `shared_ptr<const vector<QPointF>>` and a `QCPScatterStyle`, or a pixel `path()` |
| `QCP::PixelLength`, `_px` | `struct PixelLength { double px = 0; };` and `namespace QCP::Literals { constexpr PixelLength operator""_px(long double); constexpr PixelLength operator""_px(unsigned long long); }` (the `Qt::Literals` pattern) | new | lollipop, callout | bare doubles whose unit the reader guesses, or an `inPixels` flag |
| `QCPDrawContext::polygon(QPolygonF)` | `void polygon(const QPolygonF& dataPoints, const QPen& pen, const QBrush& brush = { })`: vertices in data units; a `QTransform` rotates and moves a shape before the call | new | asteroids | `polygon(std::span<const QCP::Position>, pen, brush)` over `QCP::Data` built by hand |
| `QCPDrawContext::polygon({...})` | `void polygon(std::initializer_list<QCP::Position> points, const QPen& pen, const QBrush& brush = { })`: each vertex in its own space | new | callout | a `std::array<QCP::Position, N>` passed as a span |
| `QCPDrawContext::rect(QRectF)` | `void rect(const QRectF& dataRect, const QPen& pen, const QBrush& brush = { })`: x is the key, y the value | new | brick-breaker | `rect(QCP::Data, QCP::Data, pen, brush)` |
| `QCPDrawContext::roundedRect` | `void roundedRect(QCP::Position a, QCP::Position b, QCP::PixelLength radius, const QPen& pen, const QBrush& brush = { })` | new | callout | `path(origin, path)` with `QPainterPath::addRoundedRect` in pixels |
| `QCPDrawContext::text(a, b, ...)` | `void text(QCP::Position a, QCP::Position b, const QString& text, const QCPTextStyle& style)`: laid out inside the box from `a` to `b`, words wrapped, `style.padding` inside the box | new | callout | `text(at, text, style)`, placed from an anchor, with no box size to wrap in |
| Call order inside one recording | every `QCPDrawContext` helper: a command recorded later is drawn over one recorded earlier, text, paths and `painter()` included | exists (behaviour differs) | asteroids (`Hud`: banner, then text), callout (pointer, box, text, corner handle) | text, paths and `painter()` replay in the QPainter pass, under the layer's GPU content, whatever the call order |
| Item order on a layer | items on one layer draw in the order they were added, text included | exists (behaviour differs) | asteroids (`Hud` added last, over every sprite) | an item's text is drawn under every GPU item of the same layer |
| `QCP::DataOffset` | `struct DataOffset { Data at; PixelOffset offset; };`, `DataOffset operator+(Data, PixelOffset)`, `DataOffset operator+(DataOffset, PixelOffset)`; `QCP::Position` gains the alternative. A recording made of it moves with the data and keeps its pixel offset, with no snapshot | new | callout | `QCP::AnchorOffset` (needs an anchor), or `path()` at a data origin; 2.x mixes fall back to a pixel snapshot and `recordEveryFrame()` |
| `operator-(QCP::Pixels, QCP::Pixels)` | `PixelOffset operator-(Pixels a, Pixels b)` | new | callout | subtracting `x` and `y` by hand |
| `QCPItem::update()`, `QCPPlottable::update()` | `void update()`: the content changed, record again on the next frame (one repaint per event-loop turn). Qt's name for it (`QWidget`, `QGraphicsItem`) | reshaped (rename) | asteroids, brick-breaker, callout, peak-fit | `contentChanged()` / `markDirty()` |
| `QCPLayoutElement::updateLayout` | `virtual void updateLayout(UpdatePhase phase)`: the layout pass, renamed so `update()` means one thing in the library ("draw me again") | reshaped (rename) | none directly; frees `update()` for the row above | `QCPLayoutElement::update(UpdatePhase)` |
| `QCPItem::changed()` | signal `void changed()`: deferred (4a), once per event-loop turn after `update()` was called | new | peak-fit | none: a user subclass needs `Q_OBJECT` and moc for a signal of its own |
| `QCPItem::createAnchor` | `QCPItemAnchor* createAnchor(const QString& name, std::function<QCP::Position()> where)`: the anchor sits wherever `where` says, in any space | reshaped | callout | `createAnchor(name, int id)` plus a pixel `switch` in `anchorPixelPosition(int id)` |
| `QCPItem` mouse handlers | protected `virtual void mousePressEvent(QCPMouseEvent* event)`, `mouseMoveEvent(QCPMouseEvent*)`, `mouseReleaseEvent(QCPMouseEvent*)`. QGraphicsItem's rule: the event arrives accepted, the base press handler ignores it, an accepted press grabs the moves and the release that follow (no pan for that drag). No interaction flag needed | reshaped | brick-breaker, callout, peak-fit | `QCPLayerable::mousePressEvent(QMouseEvent*, const QVariant& details)` and `mouseMoveEvent(QMouseEvent*, const QPointF& startPos)`, in pixels, undocumented |

| `QCPItem::dataRect()` | `QRectF dataRect() const`: the recording's data box, x the key range, y the value range, normalized, pens excluded | new | brick-breaker | `dataExtent()` returning `std::optional<QCPItemExtent>` with a `QCPDataBox` |

The plottable virtual `bool QCPAbstractPlottable::keyPress(QKeyEvent*)` is deleted: plottables no longer get keys, code outside an object connects to the signal | new | asteroids, brick-breaker | the plottable virtual `keyPress()`, offered to every plottable; items never get keys |

The plot takes the keyboard when its window activates only when it is the window's first Tab-focus widget (as in these single-widget targets); in a larger window the application still calls `setFocus()`. | `QCustomPlot::addAxisRect` | `QCPHandle<QCPAxisRect> addAxisRect(const QCPAxisRectOptions& options = { })`: a new rect in a new row under the last one | new | peak-fit | `new QCPAxisRect` + `plotLayout()->addElement()` + `linkTo()` + `setTickLabels(false)` + `QCPAlignmentGroup::create()` |

The name then stretches; a neutral name (`QCP::FrameRatio`) is the alternative if the maintainer prefers it | exists (behaviour differs) | lollipop | the recording replayed fitted to its data box; a custom icon records into a frame it does not know (`QCPBars` records an invisible rect to set the box) |
| `QCPAxisRect::xAxis()`, `yAxis()` | `QCPHandle<QCPAxis> xAxis() const; QCPHandle<QCPAxis> yAxis() const;`: the rect's first bottom and left axes, the pair `add<T>` binds to. ## Used as they are today

These are already the nice form, and the targets use them unchanged: `plot.axisRect()`, `QCPHandle` (`->`,
`remove()`, conversion to `T*` for `connect`), chained `setName` / `setPen` / `setBrush`, `setSelectable`,
`setInteractions`, `QCPGraph::setData(std::vector<double>, std::vector<double>)`, `QCPAxis::setRange` /
`setVisible` / `setLabel`, `plot.legend`, `rescaleAxes()`, `setBackground()`, the
position types `QCP::Data`, `QCP::AxisRatio`, `QCP::DataXRatioY`, `QCP::PixelOffset`, `QCPDrawContext::rect(a, b, pen,
brush)` and `text(at, text, style)`, `QCPTextStyle` (an aggregate, so designated initializers work as declared:
`font, color, pen, brush, alignment, textFlags, rotationDegrees, padding, mathText`), and an anchored position
written with its unit, `anchor + QCP::PixelOffset { dx, dy }` (`QCP::AnchorOffset`, `QCPItemPosition::set()`).
The 2.x form, `setParentAnchor()` then `setCoords()`, is not used: its numbers become pixels without saying so.
